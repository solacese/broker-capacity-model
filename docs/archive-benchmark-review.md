## A better saturation strategy

1. **Qualify the load path before optimizing the search.** Run SDKPerf publishers and consumers on separate Linux hosts close to the broker. Increase generator resources at an apparent ceiling; if the ceiling moves, retain a generator-conditioned/censored observation. Record actual CPU, memory, disk, NIC, broker build and topology rather than using the service-class name as a hardware description. Solace's [performance methodology](https://solace.com/products/performance/) monitors clients specifically to avoid client bottlenecks. The [SolaceLabs performance harness](https://github.com/SolaceLabs/solace-perftest-harness) already orchestrates SDKPerf on remote Linux hosts and implements exponential/binary searches. Reuse its load plane rather than building another traffic engine.

2. **Seed a bracket from genuinely comparable measurements.** Use a nearby qualified workload or matched reference as a starting hint. Ramp up/down until a sustainable/unsustainable bracket exists, then split it geometrically in rate. Do not treat a configuration guardrail or generator limit as an unsafe broker endpoint.

3. **Spend time in proportion to uncertainty.** Scout for 30 seconds, stop obvious overload early, and extend ambiguous observations to 60/120 seconds or a predeclared longer maximum. For backlog growth, use time blocks and autocorrelation-aware uncertainty estimates with predeclared sequential checks or a valid confidence-sequence method. A naive repeated p-value test would inflate false alarms. Require reconciled unique receipts, ACKs/data counters, repeatable near-boundary behavior and longer confirmations; an after-drain catch-up cannot erase in-window growth. A latency criterion requires an explicit latency SLO. This is a proposed detector revision, not a claim that the current heuristic implements these statistics.

4. **Learn a resource model, then select informative workloads.** Start with separate message-processing, ingress-byte, egress-byte and persistent-storage budgets. Useful features include offered messages/s, payload bytes/s, delivery copies/s and delivery bytes/s. Separate ingress and egress limits rather than assuming a full-duplex NIC has one summed capacity. Fit a simple monotone model plus residual interactions; use hardware/build/HA as conditioning features. Mixtures and resource interactions require their own follow-up experiments.

5. **Use the 2,000 as a candidate pool.** Begin with the 100 anchors, then select batches of 20–40 using model uncertainty near the boundary plus coverage/diversity. Keep some randomized controls, repeats and a frozen holdout. Stop when held-out interval coverage and prediction error meet a declared objective, rather than executing every easy interior point. The general idea is [level-set estimation](https://proceedings.mlr.press/v151/mason22a.html): learn where a threshold is crossed, rather than only maximize a noisy scalar throughput. The batch sizes here are proposed operating choices, not literature guarantees.

For initial training, preserve confirmed rate intervals, right/left censoring, detector reasons, measurement horizon and per-broker/run group IDs. Do not replace a bound by an invented exact maximum or distribute related stages/repeats across train and test.
